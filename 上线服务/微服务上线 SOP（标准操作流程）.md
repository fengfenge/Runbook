微服务上线 SOP（标准操作流程）

## 详细步骤

### 步骤1：上线申请（T-3天）

**执行人**: 开发负责人
**交付物**: 上线申请单

- [ ] 填写《微服务上线申请表》
- [ ] 附上架构设计文档（含依赖关系图）
- [ ] 附上性能测试报告（QPS、RT、资源占用）
- [ ] 附上回滚方案（数据库回滚脚本、配置回滚命令）
- [ ] 在 Jira 创建上线工单，关联至 Epic

------

### 步骤2：SRE技术评审（T-2天）

**执行人**: SRE工程师
**时间要求**: 申请提交后24小时内完成

- [ ] 评审资源需求（CPU/内存/存储/带宽）
- [ ] 确认服务依赖健康（下游服务SLA、数据库连接池）
- [ ] 检查日志规范（结构化日志、TraceID注入）
- [ ] 检查监控覆盖（黄金四指标：延迟、流量、错误、饱和度）
- [ ] 确认CI/CD流水线配置正确
- [ ] 在 Jira 工单中填写评审意见

**评审通过标准**:

- 资源利用率预估 ≤ 70%（峰值）
- 所有下游依赖有降级方案
- 监控告警已配置且测试通过

------

### 步骤3：安全扫描（T-2天）

**执行人**: 安全工程师

- [ ] 容器镜像漏洞扫描（Trivy/Clair）
- [ ] 依赖组件安全审计（SCA工具）
- [ ] 敏感信息泄露检查（密钥、密码硬编码）
- [ ] API接口权限设计评审
- [ ] 在 Jira 工单中上传扫描报告

------

### 步骤4：运维经理审批（T-1天）

**执行人**: 运维经理

- [ ] 确认上线窗口期（避开业务高峰）
- [ ] 确认值班安排（发布期间SRE在岗）
- [ ] 确认回滚决策人（明确授权）
- [ ] 在 Jira 工单中审批通过

------

### 步骤5：灰度发布（上线日）

**执行人**: SRE工程师
**时间窗口**: 业务低峰期

#### 5.1 发布前检查

- [ ] 确认生产集群状态正常（kubectl get nodes）
- [ ] 确认监控大盘无异常告警
- [ ] 确认数据库备份已完成
- [ ] 通知值班群：「服务X灰度发布开始，值班人@xxx」

#### 5.2 灰度执行

| 批次   | 比例 | 观察时间 | 检查项                        |
| :----- | :--- | :------- | :---------------------------- |
| 第一批 | 5%   | 15分钟   | 错误率、P99延迟、业务核心接口 |
| 第二批 | 20%  | 15分钟   | 同上 + 资源使用率趋势         |
| 第三批 | 50%  | 15分钟   | 同上 + 下游服务负载           |
| 全量   | 100% | 30分钟   | 全面验证 + 业务验收           |

**每批次检查命令**:

```bash
# 查看Pod状态
kubectl get pods -n prod -l app=<service-name> -w

# 查看错误率
curl -s "http://prometheus:9090/api/v1/query?query=rate(http_requests_total{job=\"<service-name>\",status=~\"5..\"}[5m])"

# 查看P99延迟
curl -s "http://prometheus:9090/api/v1/query?query=histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{job=\"<service-name>\"}[5m]))"
```

#### 5.3 灰度通过标准

- [ ] 错误率 < 0.1%
- [ ] P99延迟 < 500ms（或基线+20%以内）
- [ ] 无新告警产生
- [ ] 业务核心接口验证通过

> ❌ **任一指标未达标 → 立即执行回滚，见步骤7**

------

### 步骤6：业务验收（全量发布后）

**执行人**: 业务负责人

- [ ] 核心业务场景端到端验证
- [ ] 用户-facing功能确认正常
- [ ] 在 Jira 工单中验收签字

------

### 步骤7：回滚方案（备用）

**触发条件**: 灰度/全量发布后指标异常，或业务验收不通过

```bash
# 方式1：Kubernetes 回滚
kubectl rollout undo deployment/<service-name> -n prod

# 方式2：指定版本回滚
kubectl rollout undo deployment/<service-name> -n prod --to-revision=<revision-id>

# 方式3：数据库回滚（如Schema变更）
# 执行预先准备的回滚脚本
mysql -h <host> -u <user> -p < rollback_v1.2_to_v1.1.sql
```

**回滚后检查**:

- [ ] 确认旧版本Pod全部Running
- [ ] 确认错误率恢复至基线
- [ ] 通知业务负责人验证
- [ ] 在 Jira 工单中记录回滚原因

------

### 步骤8：复盘归档（发布后3天内）

**执行人**: SRE工程师 + 开发负责人

- [ ] 填写《上线复盘报告》
- [ ] 更新服务Runbook（如有新发现）
- [ ] 更新CMDB（服务信息、依赖关系）
- [ ] 关闭Jira工单

## 验证步骤

- [ ] 错误率恢复至 < 0.1%
- [ ] P99延迟恢复至 < 500ms
- [ ] 无新告警产生
- [ ] 业务核心接口验证通过

------

## 回滚方案

```bash
# 如扩容后问题未缓解，执行回滚
kubectl rollout undo deployment/<service-name> -n prod

# 确认回滚成功
kubectl get pods -n prod -l app=<service-name>
kubectl rollout status deployment/<service-name> -n prod
```
